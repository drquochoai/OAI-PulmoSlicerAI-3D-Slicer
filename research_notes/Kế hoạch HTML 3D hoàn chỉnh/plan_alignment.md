# Alignment with PulmoSlicerAI planning and Slicer architecture

## Which planning files, contracts, work orders, and gates must be extended, and in what sequence?

### Takeaway
The repository already has a disciplined export boundary, but it has no planned interactive-HTML capability: `EX04` is only an STL/OBJ display-mesh exporter. The HTML viewer should therefore be added as a new versioned derivative-export capability under `ExporterPort`, not embedded in segmentation/PTL code, and should enter the existing S9/G6 export slice with its own requirements, modules, tests, risks, source/license records, and acceptance evidence.

### Cited Findings
- The architecture is a local modular monolith with ports/adapters; export is explicitly behind `ExporterPort`, the Slicer presentation layer must not call VTK/Torch directly, and worker crashes must leave the UI usable with a PHI-safe error link. This is the correct boundary for HTML generation. — [Architecture](../../planning/02_ARCHITECTURE.md)
- The planning corpus is explicitly `DESIGN ONLY`; implementation claims require runtime evidence, not the presence of files or an exit code. — [Start here](../../planning/00_START_HERE.md); [Release gates](../../planning/18_GATES_AND_ACCEPTANCE.md)
- Current export modules are `EX01` NRRD, `EX02/EX03` DICOM SEG and roundtrip validation, `EX04` STL/OBJ “for display only,” and `EX05` research report. There is no HTML viewer exporter or HTML integrity validator in the module catalog. — [Module catalog](../../planning/catalogs/MODULE_CATALOG.csv)
- Existing S9/G6 covers exports, reports, offline setup/uninstall, and Windows roundtrip; `WO-10` requires state correctness, resumability, memory budget, privacy, provenance, positive/negative tests, and an evidence pack. — [Phased build plan](../../planning/27_PHASED_BUILD_PLAN.md); [WO-10](../../planning/workorders/WO-10_EXPORT_AND_OFFLINE_INSTALL.md)
- Public interfaces require a contract version, types, units, coordinate frame, deterministic policy, errors, and test IDs; geometry, ontology, and review state are protected core and changes require an ADR plus software/domain review. — [Modular coding standard](../../planning/03_MODULAR_CODING_STANDARD.md)
- Every artifact contract must carry SemVer, random artifact/case IDs, source hashes, creation/software/model provenance, coordinate frame, units, status, warnings, and validation-report reference. `COMPLETE` means technically valid, not clinically reviewed. — [Contracts and versioning](../../planning/04_CONTRACTS_AND_VERSIONING.md)
- G6 currently requires clean offline Windows install/uninstall/rollback and correct DICOM SEG roundtrip; quality gates reject false success, data deletion, or missing evidence. HTML export should add criteria to G6 rather than weaken or replace these requirements. — [Release gates](../../planning/18_GATES_AND_ACCEPTANCE.md)

### Inferences
- Planning update order should be: (1) add an ADR for “single-file offline HTML display derivative”; (2) register Three.js/viewer dependencies, exact versions, licenses, hashes and redistribution terms in `SOURCE_REGISTER`; (3) add explicit functional/nonfunctional/security requirements and traceability; (4) define a versioned `InteractiveHtmlExportManifest`/DTO and error enum; (5) add new module entries rather than overloading `EX04`, for example an HTML scene builder, mesh optimizer, single-file packager, and offline validator; (6) extend `UI12` and `AP08`; (7) expand `WO-10`, `TASK_BACKLOG`, `TEST_MATRIX`, and `RISK_REGISTER`; (8) add the work to S9/G6; (9) only then implement and produce Windows/browser evidence.
- The anatomy selection belongs in the export request/manifest. Its default should be “all currently valid eligible structures,” resolved at click time, while missing/invalid structures are listed as excluded with reasons. Eligible scope: lungs/lobes, segmental B/A/V, lesion/tumor, aorta/arch branches, ribs, sternum, and T1–T12. Clavicles, scapulae, and costal cartilage must not be generated merely for HTML export.
- HTML export must consume existing validated artifacts and cached closed surfaces. It must never cause TotalSegmentator/PTL or other AI to rerun implicitly; absent anatomy should produce a clear exclusion/warning or a separate explicit reconstruction action.
- A new export error family is warranted, such as `NO_ELIGIBLE_SURFACES`, `INVALID_DISPLAY_GEOMETRY`, `HTML_PAYLOAD_TOO_LARGE`, `HTML_INTEGRITY_FAILED`, `UNSUPPORTED_BROWSER_PROFILE`, `EXPORT_CANCELLED`, and `PHI_SCAN_FAILED`, mapped to real UI handlers.
- The single HTML is a display/review derivative, not a DICOM SEG replacement and not an artifact from which clinical measurements or source masks are recovered.

### Gaps
- The planning files say the product is design-only, while the conversation describes a working extension. A final implementation plan must audit the actual code/modules and reconcile real status with the planning catalogs before assigning module IDs or claiming dependencies are present.
- Exact supported Edge/Chrome versions, maximum supported file size, and redistribution/license approval for the chosen JavaScript/decoder packages are not yet pinned.
- Aortic subpart splitting and arch-branch ontology are not present in the reviewed core contracts; adding them may require protected-core ADR/domain review rather than treating display names as authoritative anatomy.

## How should Subject Hierarchy, IDs, geometry, display derivatives, colors, logs, progress, cancellation, resumability, and failure isolation work?

### Takeaway
The HTML must be generated from immutable, anatomically identified source artifacts through a separately validated display-mesh pipeline. The browser tree is a serialized view of stable ontology IDs and Slicer hierarchy—not a reconstruction from display names—and every coordinate/color/smoothing operation must be explicit, versioned, reversible at the view layer, and incapable of modifying the native masks.

### Cited Findings
- The architecture’s core decision is “segmentation source remains original; display mesh is derivative; measurement geometry comes from mask/affine.” Branches are instances with unique IDs and lineage, not merely semantic voxel classes. — [Architecture](../../planning/02_ARCHITECTURE.md)
- `BranchInstance` must have stable ID, parent IDs, child IDs, centerline, junctions, source label, confidence, status and mask link; pulmonary veins may be a forest rather than a forced single-root tree. — [PTL graph adapter](../../planning/08_PTL_GRAPH_ADAPTER.md)
- Slicer uses RAS internally, while DICOM/ITK and most file exchange use LPS; RAS and LPS differ by sign inversion of the first two axes. — [Official Slicer coordinate documentation](https://slicer.readthedocs.io/en/latest/user_guide/coordinate_systems.html)
- The project contract standard is LPS millimetres, with explicit coordinate system, forward/inverse affine and phantom tests; an asymmetric left/right phantom is mandatory. — [Contracts and versioning](../../planning/04_CONTRACTS_AND_VERSIONING.md); [DICOM geometry](../../planning/05_DICOM_GEOMETRY.md)
- Slicer Subject Hierarchy supports arbitrary folder structures and eye-icon visibility; Segmentations appear as nodes with contained segments in a virtual branch. — [Official Slicer UI documentation](https://slicer.readthedocs.io/en/latest/user_guide/user_interface.html); [Official Segmentations documentation](https://slicer.readthedocs.io/en/5.12.0/user_guide/modules/segmentations.html)
- Slicer segments can hold binary-labelmap and closed-surface representations; strong smoothing can shrink a segment, and a smoothing factor of zero speeds updates. — [Official Segment Editor documentation](https://slicer.readthedocs.io/en/5.8/user_guide/modules/segmenteditor.html)
- Existing UX requires lazy actors/LOD, asynchronous progress, responsive Qt main thread, visibility changes without rerunning computation, and text/legend/opacity support instead of color-only meaning. — [Slicer UX](../../planning/12_SLICER_UX.md)
- Changing color or camera only invalidates the view cache; changing source CT/affine invalidates all derivatives. — [Contracts and versioning](../../planning/04_CONTRACTS_AND_VERSIONING.md)
- The planned negative test for `EX04` explicitly requires detecting/rejecting degradation when smoothing loses a 1 mm branch, while the original mask remains unchanged. — [Test matrix, TEST-EX04-N](../../planning/catalogs/TEST_MATRIX.csv)
- The job model distinguishes queued/admitted/running/writing/validating/complete and blocked/failed/cancelled/stale states; cancellation must terminate the process group, quarantine incomplete output, and never create a false `COMPLETE`. Atomic partial-write, checksum validation, and resumability are already required. — [Scheduler and storage](../../planning/11_SCHEDULER_STORAGE.md); [Contracts and versioning](../../planning/04_CONTRACTS_AND_VERSIONING.md)

### Inferences
- Use a stable export-tree manifest whose node key is a versioned ontology/branch/artifact ID, never MRML node ID or localized display text. Store separate fields for `stable_id`, `parent_id`, Vietnamese/English display names, anatomical system, side, lobe, segment number, source artifact hash, review state, visibility, color, opacity, and mesh-chunk reference.
- Mirror the user-facing hierarchy: `Lungs > Right/Left > Lobe > Lung/B/A/V`, with separate `Tumor`, `Aorta`, and `Chest wall` roots. Preserve multi-parent/forest provenance in metadata even if the UI must show a primary display parent; do not fabricate a single pulmonary-vein root.
- Treat the Slicer Subject Hierarchy as presentation organization, not the sole source of clinical identity. Attach stable attributes to nodes/segments and generate both Slicer folders and the HTML tree from the same typed hierarchy descriptor.
- Geometry pipeline: read the closed surface in Slicer RAS (including any applied parent transform), harden/compose transforms into world coordinates, convert exactly once into the documented web coordinate frame, store units in millimetres, recompute bounds/normals, and reverse triangle winding whenever the transform determinant is negative. The export manifest should retain the exact 4×4 source-to-web transform and orientation labels.
- Test geometry with asymmetric left/right/anterior markers, oblique transforms, parent transforms, normals/back-face culling, bounding boxes, and roundtrip landmark coordinates. A visually plausible rendering is not sufficient evidence.
- Smoothing and decimation operate only on a copy of the closed-surface derivative. Preserve native masks, source closed surface, and measurement geometry unchanged. Use anatomy-specific presets: topology/branch-preserving settings for B/A/V and tumor; moderate settings for lobes/aorta; more aggressive decimation for ribs/sternum/T-spine. Run component-count, branch-endpoint, minimum-radius, Hausdorff/surface-distance, bounds, triangle quality and self-intersection checks with thresholds pre-registered per anatomy. If a critical small branch fails, keep the unsmoothed mesh and warn rather than silently deleting it.
- A color-template registry should be a versioned view artifact. It needs stable semantic roles (artery, vein, airway, lung/lobe, tumor, aorta, bone, uncertainty), explicit RGB/sRGB values, opacity and contrast/accessibility metadata. “Apply template” changes only the HTML/export view cache; it cannot change labels, confidence, review state or trigger AI. Text labels and legend remain mandatory because color alone is unsafe.
- The HTML export should be a `CPU_LIGHT`/possibly `IO_LIGHT` job with visible substages: collect eligible structures; create/reuse closed surfaces; smooth/decimate with QA; convert coordinates; compress chunks; assemble single HTML; PHI scan; integrity validate; atomic commit. Show one updating progress row, elapsed time, current structure and byte/triangle counts, plus CPU/RAM telemetry where available.
- Cancel at safe checkpoints; write to `.partial`; preserve prior successful export; on resume, reuse per-structure chunks keyed by source hash + smoothing/LOD/color-template/tool-version parameters. A change in color should reuse geometry and rebuild only the view manifest/container; a source mask/affine change invalidates the corresponding geometry chunk.
- Failure isolation: browser export failure must not change MRML source nodes, segmentation review state, or AI artifacts. Validation failure leaves the partial file quarantined and the export job `FAILED_RETRYABLE/FATAL` with a safe error. The final `.html` is promoted only after size bounds, internal manifest, hashes, PHI scan and offline smoke load pass.

### Gaps
- Exact clinical/anatomical color palette is not specified. It needs domain-owner approval, color-blind/accessibility review, and versioning; “similar appearance” alone is not a testable definition.
- Smoothing/decimation thresholds for tiny vessels are not specified and cannot be chosen from visual preference alone; they require representative CT/mesh benchmarks and clinician review.
- The exact source of aorta ascending/arch/descending boundaries and handling of anatomical variants remains undefined.

## What acceptance tests/release gates already apply, and what file:// all-in-one risks must be added?

### Takeaway
The existing G5/G6 quality, performance, privacy, atomicity, offline-Windows and negative-test policies already apply. Single-file HTML adds a browser/runtime test surface: no external requests, local-file compatibility, embedded dependency integrity, bounded memory/startup, GPU-context loss handling, orientation correctness, accessibility, and clear research-only status must all be proven on pinned browsers and target hardware.

### Cited Findings
- G5 prohibits performance gains that lose critical branches or cause paging; G6 requires clean Windows offline operation, rollback, and preservation of patient data. Provisional QoS must be measured rather than declared passed. — [Release gates](../../planning/18_GATES_AND_ACCEPTANCE.md)
- Existing performance policy prioritizes geometry correctness and critical-branch preservation before speed, uses lazy LOD, and requires measured p90/quality parity rather than assumptions based on hardware names. — [Performance architecture](../../planning/10_PERFORMANCE_CPU_AMD.md)
- Existing cross-tests include fast LOD dropping a visible small branch (`X013`), Windows offline install (`X018`), partial-write crash recovery (`X020`), and human misinterpretation caused by color alone (`X023`). — [Test matrix](../../planning/catalogs/TEST_MATRIX.csv)
- Runtime is local-first with no Internet requirement, no default telemetry/cloud sync, PHI-free logs/screenshots/crash reports, and a required scan of diagnostic filenames/paths. Dependencies require pinned versions, licenses, SHA256, SBOM and CVE/SCA review. — [Security and privacy](../../planning/13_SECURITY_PRIVACY.md)
- Atomic artifacts require `.partial`, validation and checksum before same-volume rename; no reviewed artifact may be deleted by cache cleanup. — [Contracts and versioning](../../planning/04_CONTRACTS_AND_VERSIONING.md)
- Official Slicer documentation warns that mesh formats may not encode anatomical coordinate systems uniformly and recommends explicit RAS/LPS convention plus integrity checking during interchange. — [Official Slicer data-loading documentation](https://slicer.readthedocs.io/en/latest/user_guide/data_loading_and_saving.html)

### Inferences
- Add positive tests: one valid structure; full default selection; missing optional structures; 100+ nodes; branch forest; Unicode labels; all template colors; opacity/isolate/show-all; mouse/touch rotate/pan/zoom; standard anatomical views; fit selection; object picking; screenshot; responsive layout; offline double-click launch in pinned Edge/Chrome; no network; valid checksum/manifest; reopen after Windows copy/email download.
- Add negative tests: mirrored left/right; negative-determinant winding; detached parent transform; empty/corrupt mesh; NaN/Inf coordinates; duplicate stable IDs; cyclic hierarchy; smoothing removes a critical branch; oversized payload; disk full; cancel at each stage; crash during write; antivirus file lock; Unicode/long path; dependency hash mismatch; malicious node text/HTML injection; PHI in title/node/path; WebGL disabled/context lost; decoder unavailable/corrupt; unsupported browser; stale source artifact; old/future manifest version.
- Test `file://` specifically. Avoid runtime fetches, ES-module imports, workers loaded from external paths, CDN fonts/icons, external textures, analytics and source maps. Inline/bundle JS, CSS, icons, decoder code and mesh payload; if workers are used, construct them from embedded Blob code and test this under the chosen Content Security Policy. Provide a readable failure panel if browser policy blocks a feature.
- All-in-one has a real tradeoff: base64/embedded payload and bundled decoder increase file size/startup memory, and very large strings can stall parsing before the 3D scene appears. Mitigate with per-node binary chunks, quantization/compression, worker decoding, lazy mesh creation, progressive initial scene, and explicit warning/limit profiles. Do not promise a universal size/load-time threshold before benchmark.
- Acceptance should include measured export duration, HTML size, peak Slicer RAM, peak browser RAM, time-to-first-interaction, time-to-all-selected-visible, median/p95 UI response, steady FPS, GPU/context-loss recovery, and visual/geometry parity across Lite/Standard/Detail profiles on the actual target machine.
- Default export selection is all valid eligible structures, but the dialog must show the resulting estimated size and allow deselection before starting. Default selection must not mean silently generating absent structures or rerunning AI.
- Privacy acceptance should inspect the complete HTML text/binary strings for patient name, MRN, source UIDs, filesystem paths and DICOM metadata; escape all labels to prevent script/markup injection; include no CT voxels by default; state “research/display derivative, not clinically verified” according to actual review state.
- Add a post-build offline validator that parses the embedded manifest, verifies every chunk hash and stable-ID reference, launches the HTML with network disabled in pinned browsers, exercises a minimal interaction script, captures PHI-safe evidence, and only then atomically marks the export complete.

### Gaps
- Browser-specific maximum practical HTML/string/Blob/WebGL resource limits vary and are not defined in repository planning. They require empirical testing on the target Edge/Chrome versions and hardware.
- Whether an enterprise browser policy permits `file://`, Blob workers, WebGL/WebGPU, or downloaded HTML varies by hospital IT and must be included in compatibility probing; a local HTTP server would violate the strict “double-click one file” requirement unless separately approved as a fallback.
- Exact quantitative pass thresholds for load time, FPS, memory, mesh deviation, and file size need benchmark baselines; planning explicitly prohibits declaring provisional goals as PASS without runtime evidence.
